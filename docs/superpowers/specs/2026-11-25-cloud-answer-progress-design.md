# 纯云端接听进度显示：设计

日期：2026-11-25。状态：待用户确认。依赖 PR #52（`contrib/cloud-answer-watch`）新增的 `CallKitActionHandling.callKitAnswerAccepted(uuid:)`。

## 意图

只有云端连接时（iPhone 不在家里 Wi-Fi，安卓在家），在 iPhone 上按下接听后要等几秒才能说话，失败时更是长时间没有任何反馈。例如安卓重启后 Shizuku 没启动，电话被接起却一直没声音，约 45 秒后才结束。用户的诉求是：

- 按下接听后能看到现在进行到哪一步、已经等了多久、通常要多久；
- 失败时尽快知道原因，以及自己能做什么。

用户按下接听后通常看着屏幕等，所以以屏幕显示为主，不做听筒提示音或手表显示。

## 目标

1. 云端接听过程中，分四个阶段显示进度；每个阶段一句标题、一句说明，并显示已等待时间。
2. 显示「平均约 N 秒」作为参考，数据取本机最近 10 次成功接通。
3. 失败时停止等待，显示具体原因和一句建议。系统通话界面关闭后，原因仍能在锁屏上看到。
4. 安卓端的语音服务（Shizuku 音频桥）不可用时，安卓端不接起运营商电话，直接报告失败，避免「接起了却没声音」。

## 非目标

- 锁屏与灵动岛实时活动的进度显示：以后再做。
- Watch 上的进度显示、听筒提示音。
- VoWLAN、VoBLE 等本地链路的接听进度：本地链路接听很快，本次只做云端。
- 修改 Relay（Worker）：作者部署成本高，Relay 额度也不稳。
- 振铃时预先建立云端语音连接：另一项提速工作，本次不做。
- 预测精确的剩余时间。

## 反目标（这样做出来就算失败）

- 显示一个经常不准的「预计 N 秒后接通」。
- 来电名字里的进度文字残留在通话记录（最近通话）、Siri、车机等任何通话结束后仍可见的地方。
- 出现 Relay、PCM、WebSocket 等内部名词。
- 进度显示本身拖慢接听，或者频繁刷新系统通话界面造成闪烁、读屏反复播报。
- 旧版本组合（新 iPhone + 旧安卓端，或旧 iPhone + 新安卓端）因新增状态出错。

## 约束

- 系统 CallKit 来电和通话界面不能放自定义视图，唯一能改的是来电名字这一行（`CXCallUpdate.localizedCallerName`）。
- 通话时手机贴近耳朵会触发接近传感器关屏，这一点已知并接受（用户看屏幕等）。
- iOS 工程为 Swift 5 语言模式。新增状态字段必须向后兼容：收到不认识的状态时，iOS 和安卓现有代码都会直接忽略。
- PushKit 冷启动时没有 AppModel，由 `ColdLaunchCallKitHandler` 接听。名字行进度在冷启动时也要生效；App 内页面这时本来就看不到。
- 平均耗时只存在本机，不上传。

## 用户已确认的文案

界面上统一写作「安卓端」。

| 阶段 | App 内标题 | App 内说明 | 名字行（例：张三 · ……） |
|---|---|---|---|
| 1 | 正在连接云端 | iPhone 正在连上云端 | 连接云端 3 秒 |
| 2 | 正在等待安卓端响应 | 安卓端连上云端后会立即接听 | 等待安卓端 3 秒 |
| 3 | 安卓端正在接听 | 接听指令已发给安卓端 | 安卓端接听中 3 秒 |
| 4 | 正在接通语音 | 电话已接起，马上就能说话 | 接通语音中 3 秒 |
| 已接通 | 恢复原有通话界面和计时 | — | 恢复原来的名字 |

**时间：**

- 默认显示「已等待 N 秒」。
- 本机有 3 次或以上成功接通记录时，显示为「已等待 N 秒 · 平均约 M 秒」。M 是最近 10 次的平均，四舍五入到整数秒。
- 已等待时间超过平均值的 2 倍、并且至少 5 秒时，说明换成「比平均慢，可能是网络较差」。

**失败：** 名字行显示「接听失败」。App 内显示以下标题和建议。

| 情况 | 标题 | 建议 |
|---|---|---|
| iPhone 连不上云端 | 无法连接云端 | 检查 iPhone 的网络 |
| 云端服务出错或额度用完 | 云端暂时不可用 | 稍后回拨对方 |
| 安卓端迟迟没连上云端 | 安卓端未上线 | 检查安卓端的网络，确认 AirSIM 在运行 |
| 安卓端语音服务不可用 | 安卓端无法传送语音 | 在安卓端启动 Shizuku 后回拨 |
| 安卓端接听出错 | 安卓端未能接起电话 | 对方可能已挂断 |
| 别的设备先接了 | 已在其他设备接听 | （无） |

## 做法

考虑过三种：

1. **iPhone 汇总现有状态，安卓端补一个状态（已选）。** iPhone 新增进度判定，输入是现有的本地事件和 Relay、安卓端状态。安卓端接听前确认语音服务，不可用时不接起，回一个新状态。
2. **只改 iPhone，靠超时推断。** 不需要协议改动，但 Shizuku 不可用时电话已经被接起，对方会听到一段无声，判定也更慢。
3. **由 Relay 汇总阶段。** 逻辑集中，但需要作者重新部署 Relay，现阶段 Relay 额度不稳定。

选第 1 种的原因：现有状态已经足以判定四个阶段，只有「语音服务不可用」需要安卓端在接起前报告，这也是唯一能避免无声通话的位置。

## 设计

### 1. 阶段判定（iPhone）

用一个纯逻辑的进度模型，输入事件，输出当前阶段、已等待时间和失败原因，单独可测。时间起点是 `callKitAnswerAccepted`，也就是 CallKit 接受接听的时刻；只对带云端媒体的推送来电生效。

| 输入（现有） | 来源 | 进入阶段 |
|---|---|---|
| CallKit 接受接听 | `callKitAnswerAccepted` | 1 正在连接云端 |
| HTTP 早期接听回执 `agentConnected == false`，或语音连接上的 `action_queued` | `submitEarlyAnswer` 回执；Relay | 2 正在等待安卓端响应 |
| 回执 `agentConnected == true`、`action_forwarded`，或排队后出现安卓端 `peer_connected` | 回执；Relay | 3 安卓端正在接听 |
| `answer_ok` | 安卓端 | 4 正在接通语音 |
| `active` | 安卓端 | 已接通 |

阶段只前进不后退。迟到的旧状态不能让阶段倒退，另一通电话的状态也不能影响当前这通，沿用现有的 call_id／call_uuid／generation 匹配。

### 2. 失败判定（iPhone）

| 失败 | 判定 |
|---|---|
| 无法连接云端 | 语音连接与 HTTP 早期接听都因网络错误失败，并且现有的有界重连全部用完 |
| 云端暂时不可用 | Relay 返回 5xx 或 429（如 `503 relay_capacity_exhausted`） |
| 安卓端未上线 | 进入阶段 2 后 10 秒内没有进入阶段 3 |
| 安卓端无法传送语音 | 收到新状态 `answer_unavailable`，原因为 `audio_bridge_unavailable`；或阶段 4 持续 15 秒没有 `active`（兜底旧版安卓端） |
| 安卓端未能接起电话 | `action_error` |
| 已在其他设备接听 | `ownership_lost` |

**失败之后：**

1. 名字行显示「接听失败」约 2 秒。
2. 恢复原名，再结束这通 CallKit 通话：对安卓端发送结束；Watch 收到 `.ended`。
3. 发一条本地通知。标题「通话未接通」，正文为「<失败标题>：<建议>」，例如「安卓端无法传送语音：在安卓端启动 Shizuku 后回拨」。「已在其他设备接听」不发通知。

**已知风险：** 失败判定的阈值（10 秒、15 秒）是初值，真机测量后可能需要调整。

### 3. 名字行（系统通话界面）

- 通过 `CXProvider.reportCall(with:updated:)` 更新 `localizedCallerName`，格式为「<原名字> · <短状态> <N> 秒」。阶段变化时立即更新，计时每秒更新一次。
- 原名字在接受接听时保存。接通、失败、通话结束时，先恢复原名，再报告接通或结束，保证通话记录里留下的是原名。
- 原名字很长时，保留短状态，截断原名字，不截断状态。
- 冷启动路径（`ColdLaunchCallKitHandler`）同样更新名字行。因此进度模型与名字行更新放在 AppModel 与冷启动都能用到的位置，例如 `IPhoneCloudCallSession` 旁边，不放在 AppModel 里。

### 4. App 内通话页

- 仅云端接听时显示：四步进度（已完成打勾、当前步骤转圈、未到的步骤灰色）、当前标题与说明、已等待时间和平均值说明。
- 失败时显示红色标题和建议。
- 替换现在只有颜色点的连接状态，用于云端接听的连接中阶段。已接通后恢复现有显示。

### 5. 平均耗时

- 每次成功接通时，记录从 CallKit 接受接听到收到 `active` 的秒数。
- 只保留最近 10 次，存在本机 UserDefaults。
- 失败、被别的设备接听、虚拟通话不计入。

### 6. 安卓端：接听前确认语音服务

- 安卓端收到云端接听（媒体连接上的 `answer` 控制，以及经命令通道转来的 HTTP 早期接听，两条入口共用同一处判断）后，先确认本机语音服务可用，再调用系统接听。可以复用现有 127.0.0.1:7580 探测结果，或做一次短超时握手。
- 不可用时：不接起电话，通过媒体连接回 `{"status":"answer_unavailable","message":"audio_bridge_unavailable","call_id","call_uuid","generation"}`，命令通道的结果也返回失败。电话在安卓端继续振铃，直到对方挂断。
- 新旧版本组合：
  - 旧 iPhone 不认识 `answer_unavailable`，会忽略它，靠原有超时结束；
  - 新 iPhone 遇到旧安卓端，没有这个状态，靠阶段 4 的 15 秒兜底。

### 7. 协议与文档

- 新增状态 `answer_unavailable`，写进现有云端通话协议文档。
- 修复说明写入 `docs/fixes/`，格式同既有文档。

## 留给实现者

- 进度模型的类型名、文件位置。优先放进现有文件，避免改工程文件；需要新文件时使用 `.superpowers/tools/pbx_insert.py`。
- 安卓端「语音服务可用」的具体判定方式，以及短超时握手的时限（建议不超过 1 秒）。
- 名字行原名过长时的截断长度。
- App 内四步进度的具体样式，沿用现有通话页风格。

## 验证

- **iPhone 单元测试：** 进度模型的阶段前进、乱序与旧通话隔离、各失败判定、平均值计算（少于 3 次不显示、最近 10 次、四舍五入）、「比平均慢」阈值、名字行文本拼接与截断、恢复原名的时机。
- **安卓端单元测试：** 语音服务不可用时不调用系统接听、返回 `answer_unavailable`，两条入口都覆盖；可用时行为不变。
- **真机验收：**
  1. 蜂窝网络、「自动」模式来电时，名字行依次显示四个阶段，接通后恢复原名，最近通话里是原名。
  2. 在安卓端停掉 Shizuku 后来电：2 秒内显示「接听失败」，收到通知，对方听到的是继续振铃，而不是接通后无声。
  3. 冷启动来电重复第 1 项。
  4. App 内通话页的四步进度和平均值显示。
