## 源码确认的问题及本次修改

1. 网络变化后的手动路由过滤只保留 100.64/10，误排除其他 VPN 的 RFC1918 地址。改为保留配对端点作为**未验证候选**，网络变化后重新做签名健康/身份检查；新 Bonjour 仍可替换未验证的旧 DHCP 地址。
2. Wi-Fi 变为不可用时原恢复任务直接返回。现在空闲状态恢复已保存候选并探测一次，让蜂窝 + VPN 不必依赖 Bonjour。既有恢复逻辑继续负责后续重试，不新增周期定时器。
3. LAN 和手动 VPN 端点同时离线时，递归 fallback 可能来回切换。现在同一轮每个端点最多访问一次，跨候选保留预期 agent ID，失败仍保留为失败；后续独立恢复可重新尝试。
4. 探测完成和日志 await 后检查取消/代际，活动通话不自动切换候选。
5. Verbose 导出标注 verbose_enabled；启用详细采集时，健康探针失败记录控制/PCM 端口及错误，不记录凭据或请求正文。

这解决的是可从代码确认的恢复缺陷，不能替代用户设备上对本次故障的复测。没有更改 Android 端口分配、VPN 配置、ACL、Relay 或 APNs；也没有更改主工作树 main。

## 复测步骤

1. 在 iPhone 的「Verbose 日志调试」打开「Verbose 模式」。保留现有日志，记录复现时间；不要在复现后先清空 Android 日志。
2. 使用 Android 配对窗口实际显示的配对端口完成手动配对；控制/PCM 端口由加密配对自动取得，不能填成无线 ADB 端口。
3. 分别测试 Tailscale 100.64/10、其他 VPN 的 10/172.16–31/192.168 地址：Wi-Fi → 蜂窝、VPN 断开再连接、App 回前台，确认重新出现签名健康验证成功。
4. 同一轮让 LAN/VPN 都不可达，确认不会在两个端点之间无限 fallback；恢复后再次验证。
5. 分别拨出、接听并检查双向音频；活动通话不应被后台健康探针换到另一端点。
6. 失败后立即分别上传两端反馈，附北京时间、VPN 产品、失败阶段及报错。若控制正常而 PCM 不通，再检查实际 PCM 端口/转发规则，不根据空闲快照猜测。

## 验证结果

### 三星热点 + Tailscale 手动配对补充

用户进一步反馈安卓显示配对成功，但 VoWLAN 离线。源码确认 `PairingServer` 保存密钥后等待同一入站接口的控制/PCM 网关 12 秒；原实现即使没有取得端口仍触发 `onSucceeded`，而 iOS 因缺失端口/路由证明拒绝完成直连。现将此分支显示为“密钥已保存，但直连网关未就绪”，并记录已有网关诊断状态；保留现有 200 注册响应供旧 iOS 识别缺失路由证明，不伪造端口、不关闭身份校验、不清除配对配置。

该修复消除安卓错误的完成提示，不代表已修复三星网关无法启动。具体原因仍需安卓 `vowlan_state` / `vowlan_lifecycle_failed` / `pcm_probe_failed` 等故障时日志确认。先前附件机型为 Nothing A059，不能代替这台三星的现场证据。当前 ADB 无设备，尚未操作用户三星。

此增量已通过 `android/phone-control-app/test.sh`（包括新增源码防回归检查）及 Standalone debug APK 完整构建。未执行真实 PairingServer 双端超时场景、未安装 debug APK；debug 签名不能视作可覆盖正式签名安装的发布包。
